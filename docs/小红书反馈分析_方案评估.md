# 小红书反馈分析：OpenClaw vs Agent+机器人+脚本 方案评估

> 基于《飞书：贴截图/文本 → 自动分析 → 日报》计划，评估两种实现路径并给出推荐。

---

## 一、你的计划核心流程

```
飞书群贴反馈（文字/截图）
    → 机器人接收
    → OCR（若为截图）
    → 调用 LLM（Agent 分析 Prompt）
    → 输出结构化 JSON
    → 存库 + 群内回复摘要
    → 每日 10:00 定时汇总成日报，发到日报群
```

**关键约束：**
- 渠道固定：**飞书**
- 输出固定：**严格 JSON**（id, summary, type, likely_modules, hypotheses, suggested_actions, impact, priority）
- 流程固定：接收 → 分析 → 存 → 回；每日汇总
- 非对话式：不需要多轮、记忆、开放式问答

---

## 二、两种方案对比（针对本计划）

| 维度 | Agent + 飞书机器人 + 脚本 | OpenClaw + 飞书 |
|------|---------------------------|-----------------|
| **飞书接入** | 飞书开放平台自建应用，直接收 webhook | OpenClaw 内置飞书渠道，配置即用 |
| **LLM 调用** | 直接调 Gemini/Claude API，完全控制 Prompt 和输出格式 | 通过 OpenClaw Agent，需适配其调用方式 |
| **结构化 JSON** | 直接要求 JSON-only，易解析 | Agent 可能掺杂说明文字，需额外解析 |
| **存储** | 自己写 Supabase/Notion 写入逻辑，简单 | 需自建 Skill 写库，或接入现有存储 |
| **日报定时** | Vercel Cron / Supabase Edge 等，一次脚本 | 用 OpenClaw 的 Heartbeat/Schedule，需写 Skill |
| **OCR（截图）** | 飞书/第三方 OCR API，在流程中调用 | 需在 Skill 中集成，或依赖模型多模态 |
| **部署** | 复用 Offerin 的 Vercel + Supabase，加几个 API | 需单独部署 OpenClaw（或托管），再配置飞书 |
| **学习成本** | 熟悉飞书开放平台 + 一次 LLM 调用 | 需学 OpenClaw Skills、Comms、配置 |

---

## 三、针对本计划的结论：**推荐 Agent + 飞书机器人 + 脚本**

### 1. 流程是固定管线，不是开放对话

你的需求是：**消息进 → 一次 LLM 分析 → JSON 出 → 存库 → 回复**。

- OpenClaw 的优势在于：24/7 对话、记忆、多轮、动态选工具。
- 当前场景不需要这些，用轻量 pipeline 更合适。

### 2. 严格 JSON 输出更易保证

分析 Prompt 要求 **只输出 JSON，不要自然语言**。

- 自建：直接 `system + user` 调用 LLM，对输出格式控制更精确。
- OpenClaw：Agent 容易在回答中加解释，需要后处理提取 JSON。

### 3. 复用现有 Offerin 基建

- 已有：Vercel、Supabase、Gemini。
- 只需增加：
  - 一个接收飞书 webhook 的 API
  - 一个调用 Gemini 的分析逻辑
  - 一个定时任务做日报
- 不必引入 OpenClaw 的运行环境和配置体系。

### 4. 飞书对接成本差不多

- 自建：在飞书开放平台创建应用、配置事件/消息、写 webhook 处理。
- OpenClaw：同样要配置飞书应用，再在 OpenClaw 里加飞书 channel。
- 在「飞书本身」上的工作量相近，但自建少一层 OpenClaw。

### 5. 实现路径简单

```
飞书 App（接收消息）
  → Vercel Serverless /api/feishu/webhook
  → 若有图：调用 OCR
  → 调用 Gemini（你的 Agent Prompt）
  → 解析 JSON，写入 Supabase feedback_analyses
  → 调飞书 API 回消息
  → Vercel Cron 每日 10:00：查过去 24h → 拼日报 → 发到日报群
```

## 四、什么时候更适合用 OpenClaw？

若将来出现以下需求，再考虑 OpenClaw 会更合适：

- **多轮对话**：例如「帮我查今天 P0 有哪些」「把这条建个飞书任务」「这周 bug 趋势总结」
- **记忆与上下文**：需要记住之前的反馈、讨论、决策
- **多任务组合**：反馈分析 + 自动建单 + 通知 + 周报，希望一个助手统一处理
- **多渠道统一**：希望飞书、Telegram、邮件等共用同一套 Agent
- **少写代码**：接受用 OpenClaw 的 Skill 和配置，替代部分自研逻辑

当前计划更偏向「单一 pipeline」，这些能力暂时用不上。

## 五、推荐落地步骤（Agent + 飞书机器人 + 脚本）

### Phase 1：MVP（约 1–2 天）

1. **飞书应用**
   - 创建企业自建应用
   - 开启：接收群消息、发送消息
   - 配置事件订阅，指向你的 webhook URL

2. **Webhook 服务**
   - 新建 `/api/feishu/webhook`（或同类路由）
   - 校验飞书签名
   - 过滤：仅处理 @ 机器人 或 以 `【小红书】` 开头
   - 若有图片：调飞书文件 API / 或第三方 OCR 得到文本

3. **分析服务**
   - 将反馈包装为 `[{id, content}]`
   - 调用 Gemini：System = Agent 分析 Prompt，User = 上述 JSON
   - 解析返回 JSON，写入 `feedback_analyses` 表
   - 调用飞书「发送消息」API，在群里回摘要

4. **存储**
   - Supabase 新建表 `feedback_analyses`（id, content, analysis_json, created_at 等）

### Phase 2：日报（约 0.5 天）

5. **定时任务**
   - 使用 Vercel Cron 或 Supabase Edge Function
   - 每天 10:00 查过去 24h 的 `feedback_analyses`
   - 按 P0 > P1 > P2 排序，生成日报文案
   - 调飞书 API 发到日报群

### Phase 3：可选增强

6. **OCR 优化**：多图、排版复杂时的识别
7. **去重**：相近内容合并
8. **Notion/飞书文档同步**：把分析结果同步到知识库

---

## 六、总结

| 项目 | 结论 |
|------|------|
| **推荐方案** | Agent + 飞书机器人 + 脚本 |
| **主要原因** | 流程固定、需严格 JSON、可复用现有基建、实现更直接 |
| **OpenClaw** | 更适合未来扩展为多轮、多任务的通用助手场景 |
